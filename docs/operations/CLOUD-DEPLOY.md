# RunF9 in the customer's own cloud (private deployment)

Everything (app, PostgreSQL database, schedules, analysis, documents, document-search index) runs
in the customer's own account. RunF9 (Hoshmand AI) stores nothing. Public guide: https://runf9.ai/deploy.

| | AWS | Azure | Google Cloud |
|---|---|---|---|
| Template | `public/deploy/aws/runf9.yaml` (CloudFormation) | `public/deploy/azure/runf9.json` (ARM) | `public/deploy/gcp/main.tf` (Terraform) |
| App | ECS Fargate + Application Load Balancer | Container Apps | Cloud Run |
| Database | RDS PostgreSQL 17, encrypted, private subnets, 14-day backups, managed master password | PostgreSQL flexible server, TLS required, 14-day backups | Cloud SQL PostgreSQL 17, connector only, PITR |
| Secrets | Secrets Manager (generated) | Container Apps secrets (you supply them) | Secret Manager (generated by Terraform) |
| AI (optional) | Amazon Bedrock via the task role | Azure OpenAI | Vertex AI via the service account |
| Checked by | `cfn-lint` | JSON + review | `terraform validate` (google provider 6.x) |
| Starts with | "Launch in AWS" (needs `RUNF9_AWS_DEPLOY_TEMPLATE_URL`, an S3 copy of the template) or upload in the console | "Deploy to Azure" button (portal reads the template from runf9.ai; CORS allowed for portal.azure.com) | Cloud Shell: `curl` the file, `terraform apply` |

Status: **preview**. The templates are linted and validated automatically, not yet installed end to
end in a real account; do the first install with the customer.

## Image

`.github/workflows/release-image.yml` builds the Dockerfile's `runtime` target and pushes
`ghcr.io/hoshmand-ai/runf9:<version>` and `:latest` with an SBOM and provenance on a `v*` tag (or by
hand). First release: `0.1.0` (10/29/2026), public, so templates pull it with no credentials
(the registry fields stay for a private mirror). The image includes the Amazon RDS CA bundle
(`/app/certs/aws-rds-global-bundle.pem`) so RDS connections stay fully verified.

## Settings the templates set

`RUNF9_DEPLOYMENT=onprem` (a private deployment: custom storage addresses allowed, CUI upload policy
of a private install), `RUNF9_DATA_LOCATION` ("Your AWS account · us-east-1"), `DATABASE_URL` +
`PGPASSWORD` from the secret store, `JWT_SECRET`, `RUNF9_ENCRYPTION_KEY`, `RUNF9_SIGNUP=open` until the
first organization exists (then switch to invite-only), and the AI settings below.

## AI in the customer's cloud (`src/lib/llm/customer-cloud-adapter.ts`)

| `RUNF9_AI_PROVIDER` | Settings | Credentials |
|---|---|---|
| `azure_openai` | `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_DEPLOYMENT`, `AZURE_OPENAI_API_VERSION` (default 2024-10-21) | `AZURE_OPENAI_API_KEY` |
| `bedrock` | `AWS_REGION`, `BEDROCK_MODEL_ID` (model or inference profile) | Task / instance role (container credentials), or `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN` |
| `vertex` | `VERTEX_PROJECT`, `VERTEX_LOCATION` (default us-east5), `VERTEX_MODEL` (Claude → Anthropic publisher; otherwise Gemini) | Cloud Run / GCE service account (metadata server), or `VERTEX_SERVICE_ACCOUNT_JSON` |

The model is the customer's choice; `RUNF9_APPROVED_MODELS`, when set, still restricts it. Every call
goes through the same governance as the other providers (org AI switch, quotas, audit without
content). Projects marked CUI or classified are still never sent to these models (they are cloud
services outside the customer's network); use an in-network model (`LLM_BASE_URL`) for those.

## Upgrades, backups, removal

- Upgrade: redeploy the template with the new image tag. Migrations run at start and are additive.
- Backups: the cloud's automated database backups; the encryption key must be kept with them.
- Removal: the templates protect the database (deletion protection / snapshot on delete). Delete the
  database explicitly when the customer asks.
